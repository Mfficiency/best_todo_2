BestToDo · Architecture proposal

How everything relates to an item — optimized & future-proof

Same product, rebuilt around one idea: an Item is a small stable core plus attachable property components — schedule, reminders, project membership, labels, recurrence, subtasks — with every change recorded in an append-only event journal. What today is a flag, a convention or a missing link becomes an explicit, typed attachment. Views stay exactly what they already are: queries over one store.

← Current model Optimized / future-proof model

Design principles

1Small core, optional components An item is identity + content. Everything else (time, alarms, project, recurrence…) is a 0..1 or 0..N attachment — “some items have alarm properties” becomes literal structure.
2Time is a range start + end (+ allDay, timezone) replace the single dueDate. A deadline is just a schedule where start == end.
3Event-sourced history Every mutation is an immutable ItemEvent. Timestamps, stats, undo, deleted-items and sync are all derived from the journal instead of stored ad-hoc.
4Views are queries Wishlist, tabs, boards, timeline, widgets: saved filters over the one store. No membership booleans baked into the item.
5Schema is versioned schemaVersion on every record + ordered migrations replace “tolerant fromJson defaults” as the evolution strategy.
6Keep what works The alarm reliability ladder (escalation, watchdog, read-back, log) is untouched — it just gains an itemId so items and wake-ups finally know each other.

Scheduling components

Schedule 0..1

  • start, end — the requested start/end date-times. Deadline-style items use start == end; blocked-time items get a real duration (Chronize can finally render height, the calendar real busy-blocks).
  • allDay — replaces the implicit “18:00 default” convention and hasExplicitTime: an all-day item has no time; a timed item's time is always intentional.
  • timezone — stored with the instant; DST handling becomes data-driven instead of code-path-driven.
  • No component = undated (today's dueDate == null → Future/“Someday”).

Recurrence 0..1

  • rrule — an RFC 5545 subset (FREQ, INTERVAL, BYDAY, UNTIL, COUNT) covers today's every-N-days and unlocks weekly-on-Tue, monthly, weekdays. The alarm model's repeatDays proves the app already wants this shape.
  • exdates[] — skip an occurrence without lying about completion.
  • Occurrences stay virtual (computed into views) until the user touches one — then it materializes as a child item (parentId + occurrence key), preserving today's proven parent/child behavior while eliminating pre-generated clutter.

Organization: projects, stages, labels

ProjectLink 0..N

A join row {itemId, projectId, stage, rank} instead of two columns on the item. Board stage and per-column order live on the membership, where they belong. Today's “at most one project” is just a UI rule; the model no longer forbids more.

Project

Gains color, icon, archived, and optional custom stages[] (default = today's todo/ongoing/closed). Stable id semantics kept. Wishlist becomes a system view/project — the 0.1.101 insight (“wishlist = a pre-filtered view, like a project”) made structural; isWish disappears.

Label 0..N

First-class {id, name, color, kind} with an item_labels join. kind: priority models high/medium/low (at most one per item, UI-enforced); kind: system covers markers like the Todo.md import's old. The single overloaded label string is gone.

History & versioning: the event journal

One mechanism replaces five ad-hoc ones. Every mutation appends an immutable event; per-item seq is the item's version number.

// item_events — append-only
{
  "eventId": "5f0c…",          // UUID
  "itemId":  "a41b…",
  "seq":     17,               // this item's 17th change ⇒ version 17
  "at":      "2026-07-17T09:31:02.114Z",
  "deviceId": "pixel-8a",      // future sync: origin of the change
  "type":    "scheduled",      // created|edited|scheduled|moved|statusChanged|…
  "patch": [ { "field": "schedule.start",
               "from": "2026-07-17T18:00",
               "to":   "2026-07-18T09:00" } ]
}

Compaction: periodic per-item snapshots (state at seq N) let old events be archived to the export bundle — the journal stays bounded like alarm_log.txt's trim, but without losing meaning. This is the same pattern the alarm subsystem already proved: append-only log + self-trim + derived views.

Storage layout

Recommended: single SQLite database

besttodo.db · drift/sqflite · WAL mode
  • items · schedules · recurrences · reminders · projects · project_links · labels · item_labels · item_events · snapshots · meta (schemaVersion)
  • Transactions end the multi-file consistency problem (task saved, stats file not, etc.); indexes make every view a cheap query; foreign keys make “delete item ⇒ cancel reminders” automatic.

Conservative alternative: keep JSON files

items.json + item_events.jsonl (append-only) + snapshots.json

Same model, journal as JSON-Lines with the proven alarm_log.txt trim/compact pattern. Keeps the current zero-dependency, errors-swallowed persistence philosophy for web/tests. The model is storage-agnostic either way — the repository interface hides the choice.

Migration path — incremental, not a rewrite

  1. Introduce the journal alongside the current model.Append events on every mutation in _saveTasks-adjacent code; change nothing else. Instant win: the detail page can show a real per-item timeline, and exports stop reconstructing.
  2. Seed history from what exists.One-time import: current timestamps + deleted_tasks.json + DailyTaskStats become best-effort seed events (marked seeded: true).
  3. Split the label string.Parse priority-*/old/tags into Label rows; keep writing the legacy string for one release (dual-write), then drop it.
  4. Schedule component.Add start/end/allDay; tolerant fromJson maps legacy dueDate on read (the codebase's proven evolution move), plus schemaVersion so it happens once per record.
  5. Reminders.Add nullable itemId + trigger to Alarm (a purely additive change to alarms.json); wire item edit UI to create/cancel them. Delivery code untouched.
  6. Flip views to queries; retire flags.Wishlist reads the system view, board reads ProjectLink, deleted page reads tombstones. Remove isWish/kanbanStatus/deleted_tasks.json writes last, when nothing reads them.
  7. (Optional) move storage to SQLite.Behind the repository interface, once the model is settled. Sync, if ever wanted, ships journal events — no redesign needed then.

✓ What this buys, concretely

  • “Wake me for this item” in two taps, surviving reschedules — the most requested missing relation.
  • Real durations: Chronize blocks with height, calendar busy-view, overlap detection.
  • Full history & undo for every item, with stats and exports as free by-products — and the existing analytics get more accurate, not different.
  • No more overloading: labels, priority, wishlist, kanban each have one obvious home.
  • Future-proof: schema versioning, storage-agnostic repository, sync-ready op log, custom saved views — all without touching the alarm reliability code that already works.
