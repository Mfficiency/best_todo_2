BestToDo · Architecture

How everything relates to an item — current state

An item in BestToDo is a Task. There is exactly one task list (tasks.json); every surface in the app — home tabs, wishlist, Chronize timeline, project boards, calendar, widgets — is a filtered view over that single list. This page maps every property an item carries today and everything that attaches to it (or pointedly doesn't). Snapshot of the dev branch, v0.1.102.

Project properties — attached by reference

Some items carry project properties: projectId + kanbanStatus on the task, resolving against a tiny separate entity.

Project 1 ← N Task.projectId

lib/models/project.dart · projects.json · ProjectService (singleton, ValueNotifier)
  • id — stable string (project_1…); tasks reference it, so renames propagate everywhere.
  • name, description — editable; immutable model with copyWith.
  • Seeded with 3 placeholders on first run; corrupt/missing file keeps in-memory seeds.

Assignment: drag a task onto a project card → sets projectId, resets stage to todo. Unassign (× on board card) clears both. Home tiles show two live pills: project name + stage.

Kanban board

lib/ui/project_board_page.dart

Three DragTarget columns (To-Do / Ongoing / Closed) — purely a view grouped by kanbanStatus filtered by projectId. No per-project ordering, no per-column ranking, no many-to-many: an item belongs to at most one project.

Alarm properties — not actually attached

Users think of “an item with an alarm”, but structurally the alarm world is a separate silo: no taskUid on Alarm, no alarmUid on Task. The two systems share nothing but the log file and the app. ✕ no reference

Alarm

lib/models/alarm.dart · alarms.json · AlarmService
  • Identity/content: uid, name, description, color (8-color palette).
  • When: hour:minute, one-off date?, isRepeating + repeatDays (Mon=1…Sun=7). nextOccurrence() is the scheduling brain.
  • Sound: melody (7 built-ins), volume 0–1, vibrate, overrideDnd.
  • Snooze: snoozeEnabled, snoozeDurationMinutes (9), snoozeMaxCount (stored, not enforced).
  • enabled — the on/off toggle.

Reliability machinery around it

alarm_service / watchdog / diagnostics / alarm_log.txt
  • Deterministic notification-id scheme derived from uid.hashCode (base+0 one-off/snooze, +1..7 weekdays, +0x10000000 watchdog).
  • Scheduling ladder: alarmClock → exactAllowWhileIdle → inexactAllowWhileIdle; OS read-back verification; independent +90 s watchdog that rings if the primary path was dropped.
  • Full-screen ring UI, escalation, boot receivers, DST-safe stepping.

Consequence of the missing link: deleting or rescheduling an item can never touch an alarm, and an alarm can't deep-link to “its” item. If an item needs a wake-up, the user maintains an alarm that merely happens to be at the right time.

History & versioning properties — what exists today

There is no revision history and no undo journal. “History” is assembled from four partial sources, three of which live outside the item:

1 · Lifecycle timestamps on the item

createdAt / completedAt / movedAt / rescheduledAt / deletedAt / autoDeleted — single slots. A second move overwrites the first; content edits (title, description, label) leave no trace at all.

2 · Deleted items Task copies

deleted_tasks.json · cap 100, trimmed on save+load

The only “archive”: full task snapshots at deletion time. Day rollover sweeps done items here (newest first). Restore puts them back with dueDate = today (wishes stay undated). Item #101 falls off the end forever.

3 · DailyTaskStats uid sets

daily_task_stats.json · one record per day

Per day (dayKey): which uids were open at day start, moved, completed, created. Aggregate membership only — it can say that an item moved that day, never from-where, to-where or when.

4 · Derived task_events derived, not stored

StorageService._deriveTaskEvents · export bundle v2 · Usage Data CSVs

At export time the timestamps are re-expanded into pseudo-events (created/updated/completed/deleted/moved/rescheduled/restored). Faithful only for the last occurrence of each kind — a reconstruction, not a record.

Adjacent audit trails (not item-scoped)

alarm_log.txt — real append-only audit of the alarm pipeline (the one true event log in the app, but for alarms). startup_history.json, app-open timestamps, SMS report log — app-level history, no item linkage.

Versioning that does exist

Export payloads carry export_version (tasks bundle = 2, settings/everything = 1 — two intentional namespaces) and imports warn on unknown versions. The task JSON schema itself is versionless; tolerant fromJson defaults are the de-facto migration strategy.

⚠ Structural gaps this model carries (the future doc addresses each one)

  • No time range. An item has one dueDate — no start/end pair, no duration, no all-day flag; “18:00 unless hasExplicitTime” is a convention, not data.
  • Alarms don't attach to items. Two parallel time systems the user must keep in sync by hand.
  • No real history. Single-slot timestamps, edits untracked, derived pseudo-events, a 100-item deletion archive.
  • label is three features in one string (tags, wishlist priority, import marker) and isWish is a view baked in as a bool.
  • Recurrence is days-interval only and duplicates the parent into child rows.
  • No schema version on the item; evolution relies on tolerant defaults. No sync/conflict story (per-file overwrite, flush: true, errors swallowed).
